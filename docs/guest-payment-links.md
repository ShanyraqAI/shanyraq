# Запрос оплаты по обычной ссылке Kaspi Pay

## Граница реализации

Завершён отдельный этап: настройки ссылки по каждому RentalProperty → расчёт остатка по финансовому учёту → подготовленный запрос → проверка актуальности → ручное копирование/выбор приложения. Данные сохраняются на сервере. Это НЕ банковская интеграция, эквайринг, создание счёта Kaspi или подтверждение оплаты.

Официальная инструкция: https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2098 — ссылка принадлежит точке продаж, сумму вводит сам гость. Приложение не добавляет `amount`, `orderId` или несуществующие банковские параметры.

Allowlist приложения намеренно узкий: `https://pay.kaspi.kz/pay/{identifier}` с буквами, цифрами, `_`, `-`, необязательным завершающим `/`. Query, fragment, credentials, нестандартные порты и преобразованный путь запрещены. Это ограничение приложения, а не официальный исчерпывающий формат ссылок и не проверка банка/получателя. Если реальная скопированная ссылка имеет другой формат, сначала проверить документацию и образец, а не снимать проверки домена.

## Пользовательский сценарий

1. Владелец: Настройки → Приём оплаты. Для каждого объекта указать название, получателя, исходную ссылку и включение. Сохранение подтверждает только сохранённую конфигурацию, не существование получателя в банке.
2. Из редактора сообщения доступен переход к брони в новой вкладке, без потери черновика; ложная постоянная метка «Оплата не настроена» убрана. Автоматическое вложение запроса в произвольный текст/фото этим этапом не реализуется — запрос передаётся отдельным проверенным текстом. Из бронирования: «Запросить оплату». Видны стоимость проживания, завершённые оплаты, возвраты, остаток и отдельный возвратный депозит.
3. Выбрать остаток / предоплату / свою сумму. Процент предоплаты автоматически не придумывается. Неизвестный получатель платежа (`paymentCollect=null`) требует явной проверки, что деньги принимает объект; `ota` блокирует запрос.
4. Проверить подготовленный текст с точной суммой и получателем. После подготовки изменение суммы создаёт новый проверяемый снимок, а не переписывает историю старого.
5. Перед копированием/выбором приложения сервер заново проверяет revision брони, реквизитов и проводок. Изменившийся снимок нельзя передать без новой подготовки.
6. Приложение и получателя выбирает сотрудник. Браузер может не поддержать Web Share/Clipboard, в том числе из-за ограничения пользовательского жеста после сетевой проверки; показывается ошибка, автоматической отправки нет. Реальные нативные приложения в этом этапе не проверялись.
7. Открытие ссылки, подготовка, копирование, выбор приложения и скриншот чека не считаются оплатой. После сверки в Kaspi Pay учётная оплата проводится существующим финансовым механизмом с его правами и аудитом, не новой кнопкой в этом диалоге.

## Данные и защита

- Новые таблицы: `KaspiPaymentMethod`, `GuestPaymentRequest`; миграция `20261017130000_guest_payment_links`. Аддитивная миграция, существующие брони и оплаты не переписываются.
- Настройки: OWNER, tenant-scoped и version CAS; запросы: актуальное право RESERVATIONS, проверяемое повторно на сервере, включая replay.
- `remaining = max(0, total - completed PAYMENT + completed REFUND)` в валюте брони. PENDING/FAILED, EXPENSE и другие валюты не входят. Депозит не прибавляется. Только KZT, положительная сумма не больше остатка. CANCELLED/NO_SHOW заблокированы.
- Одна конфигурация на RentalProperty; composite FK не позволяют связать запрос с чужой бронью/объектом. SQL CHECK защищают положительную сумму, KZT, версию и форму SHA256.
- UUIDv4 operation key и сохранённый OperationReceipt; дополнительно digest снимка предотвращает дубли с новым ключом. Подготовленный запрос, audit и replay-результат коммитятся одной транзакцией. При ошибке финансовая операция не создаётся.
- POST: same-origin, ограниченный body, строгая schema, scope header, billing write guard, rate limit. Ответы private/no-store. Управляющие символы в названиях/получателе запрещены.
- Audit хранит идентификаторы, сумму, версию и признак «не платёж», не полный текст, URL или секреты. В запросе хранится снимок текста, нужный для истории и проверки.
- Проверка перед ручной передачей не блокирует будущую оплату или изменения после этой проверки. Ссылка обычная, гость вводит сумму; это не банковская гарантия согласованности.

## Включение и откат

`GUEST_PAYMENT_LINKS_ENABLED` по умолчанию выключен. Пока значение не равно `true`, API не обращается к новым таблицам и интерфейс не обещает работающую оплату. Отдельный read-only deployment gate проверяет их колонки только при включённой функции. Существующие проверки схемы не ослаблены.

1. Проверить миграцию, сделать backup и сначала применить её только к отдельной Preview DB штатным процессом проекта. Не применять миграции к production для исправления Preview.
2. Выполнить `prisma generate`, полный CI/build и интеграционные тесты на полной копии репозитория. Проверить Preview с включённым флагом и собственной скопированной ссылкой без реального платежа.
3. Выпуск в production — отдельный проверенный релиз: reviewed migration, backup, нужная DB, затем флаг и rebuild/read-only gate. Команда миграции production в этом этапе не запускалась, одобрение релиза автоматически не выставлялось.
4. Откат: выключить флаг, сохранив таблицы и историю. Не удалять реальные данные и не откатывать финансовые проводки. Деструктивная обратная миграция не нужна для выключения функции.

## Что остаётся за пределами этого этапа

- SMS-провайдер, серверные credentials, sender, согласие/тарификация и оплачиваемая отправка не подтверждены. В настройках явно указано «Не настроено · SMS не отправляются». Рабочий SMS/OTP не заявлен; генерация и проверка OTP, TTL, попытки, resend, одноразовое потребление и привязка к версии документа ещё требуют реализации с подтверждённым провайдером.
- Для двусторонних комплектов документов нужны выбранная модель (владелец первым / гость первым / оферта-акцепт), правовая проверка и сервис подписания. Существующее подтверждение одного документа по ссылке с вводом имени не выдаётся за SMS, ЭЦП или двустороннюю юридическую подпись. Пакетное подписание этим изменением не реализовано.
- Vercel требует повторного подключения пользователем. Production/Preview deployment, внешние банковские вызовы, SMS и подписи не выполнялись. Полный исходный запрос не считается закрытым до этих этапов и полной релизной проверки.
