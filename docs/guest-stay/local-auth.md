# Локальный вход

Локальное приложение использует ту базу, которая указана в `DATABASE_URL`. Аккаунт из production не появится в новой локальной базе автоматически. Общего логина/пароля в репозитории нет: demo seed создаёт пользователя без `passwordHash`, поэтому он не является готовой учётной записью для входа.

## Обычный путь

1. Создайте отдельную локальную PostgreSQL UTF8 базу. Скопируйте `.env.example` в `.env`; задайте её `DATABASE_URL` и `APP_URL=http://localhost:3000`. Не используйте production URL и не запускайте demo/reset на рабочей базе.
2. Выполните `npm ci`, `npm run db:migrate`, `npm run dev`.
3. Откройте `http://localhost:3000/register`. Для реального подтверждения почты нужны настроенные `RESEND_API_KEY`, `EMAIL_FROM` (разрешённый провайдером отправитель) и `VERIFICATION_CODE_SECRET` длиной не менее 32 символов. Секреты храните в `.env`, не коммитьте и не присылайте в чат.
4. Зарегистрируйте адрес, к которому у вас есть доступ, и подтвердите код из письма. Затем входите через `http://localhost:3000/login` с этим email и выбранным паролем, завершите onboarding.

Это отправляет настоящее письмо через Resend; запускайте регистрацию только со своей согласованной конфигурацией провайдера. Сам код не выводится в консоль вместо отправки. Участие в существующем workspace требует его обычного приглашения/доступа.

Альтернатива — существующий Google OAuth: настройте `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` и разрешённый redirect URI `http://localhost:3000/api/auth/google/callback` у провайдера. Кнопка Google появляется только при наличии конфигурации. Не копируйте production секреты ради локального теста.

## Без внешних провайдеров

Браузерные E2E этой ветки не проходят регистрацию: интеграционный тест создаёт одноразового синтетического OWNER и серверную сессию только в loopback fixture-базе, затем Playwright использует эту сессию. У такого fixture нет пароля для ручного входа. Это не отключает серверную авторизацию и не добавляет обход в `/login`.

Если нужен ручной локальный аккаунт без почты/Google, отдельно подготовьте согласованный disposable-only provisioner; не отключайте проверку email или tenant/role guard в приложении. Существующий `test:provision:phase2` предназначен для своих фазовых E2E, может менять пароли тестовых пользователей, выдаёт SUPER_ADMIN и выводит тестовые credentials — это не рекомендуемый обычный путь входа.
