# Финансовая аналитика бронирований

## Определения и источники

| Показатель | Источник / правило | Статус |
| --- | --- | --- |
| Сумма комнат и сумма бронирования | `rooms[].amount` и `amount` из Channex revision; сумма бронирования распределяется по комнатам пропорционально `rooms[].amount` | Channex, фактическое значение из сообщения; распределение по единицам расчётное |
| Валюта | `currency` Channex для импортированной брони; валюта бронирования для ручной записи операции | Фактический код валюты; разные коды не суммируются |
| Комиссия OTA | `ota_commission`, когда присутствует; иначе ручная настройка канала: `сумма комнаты × ставка / 100 + фиксированный сбор × доля комнаты` | Channex — фактическая переданная комиссия; настройка — оценка. Источник и ставка сохраняются на бронировании |
| Дополнительные услуги/сборы | Безопасный набор `services`: название, тип, сумма, `excluded` и `room_index`; без индекса сумма распределяется по комнатам пропорционально | Channex, только если поле передано. Не складывается повторно с общей суммой |
| Налоги | В revision нет унифицированного поля с суммой, валютой и ответственным за сбор налогов | Нет данных; не вычитаются из суммы |
| Кто собирает оплату / вид оплаты | `payment_collect`, `payment_type` | Channex. Указывает план сбора/тип, но не подтверждает получение денег |
| Оплата и возврат | Вручную записанные операции; старые поля депозита учитываются только при отметках даты получения/возврата | Ручная запись; Channex Payment Application не подключён к синхронизации |
| Ожидаемая/фактическая выплата объекту | Для канальных выплат не хватает подтверждённой payout/settlement операции | Нет данных; не выводится из комиссии |
| Расход | Ручная операция `EXPENSE`, привязанная к бронированию | Ручная запись |
| Чистый доход / чистая прибыль | Не вычисляется: неизвестны сбор налогов и фактические удержания/выплаты; прибыль также требует полного набора расходов | Нет данных |

Операции хранятся как Decimal с валютой, объектом, организацией, бронированием, датой, статусом, способом и типом. Возвраты ограничены суммой записанных завершённых оплат. Платёжные реквизиты карт не принимаются и не сохраняются. Ручные изменения ставки и финансовые операции попадают в журнал аудита.

## Channex: подтверждённые пределы

Страница Channex [Bookings Collection](https://docs.channex.io/api-v.1-documentation/bookings-collection) описывает поля `amount`, `currency`, `rooms`, `services`, `payment_collect`, `payment_type`, `ota_commission` и revision statuses `new`, `modified`, `cancelled`. В документации прямо сказано, что `ota_commission` сейчас доступна для Booking.com и Airbnb. Поэтому в текущей интеграции фактическую комиссию можно считать подтверждённой только при наличии самого поля; прочие названия OTA нельзя объявлять поддерживаемыми источниками фактической комиссии.

Payload зависит от OTA и не гарантирует услуги, комиссию или `payment_collect`. Налоговые данные, кто обязан перечислять налоги, факт оплаты гостем, перевод средств OTA, возврат и сумма удержания в стандартной booking revision не установлены. Channex [Payment Application API](https://docs.channex.io/api-v.1-documentation/payment-application-api) отдельно содержит статусы платежей/транзакций, но Shanyraq не запрашивает их. В revision нет per-room commission/tax splits: комиссия распределяется по сумме комнат, а если суммы комнат недоступны — поровну. Для услуг используется переданный `room_index`, иначе сумма распределяется пропорционально сумме комнаты.

Подключённого инструмента чтения аккаунта/API Channex в среде разработки нет, а действующий реальный payload не был доступен. Ограничения выше основаны на опубликованной документации и текущем парсере, а не на тесте production-каналов. Для Krisha.kz, Ostrovok/ETG, Bronevik, Expedia и других источников отдельные гарантии полей не подтверждены; настройка комиссии остаётся оценочной.

## Совместимость и включение

Существующие бронирования сохраняют прежнюю сумму и получают `null` в новых финансовых полях, это не трактуется как ноль. Новые комиссии применяются при следующем новом/изменённом Channex revision; уже сохранённая история не пересчитывается при редактировании ставки. Для включения оценки оператору нужно внести процент и/или фиксированный сбор по каналу. Для фактических оплат/возвратов расходы записываются вручную. Применение миграции: `npx prisma migrate deploy` после настройки `DATABASE_URL` на нужную базу и проверки миграции; здесь миграция не выполнялась.
