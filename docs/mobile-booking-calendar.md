# Мобильный календарь и дальнейшие этапы Shanyraq

## Статус

Первый этап реализован в feature-ветке, но **не готов к production-релизу**: нет полного checkout/build и прогона на одноразовой PostgreSQL с полной историей миграций. Staging и реальные iOS/Android не проверены. Следующие этапы не реализованы: переход к денежным изменениям заблокирован воротами надёжности, а не заменён макетами.

Исходная main: `213a4aaece3639a13684c50a8d92dccd17bf4e38`. Прочитаны AGENTS.md, README, Prisma schema, общий/mobile календарь, мастер/карточка брони, reservation service/actions, finance actions, документы/actions, signing/security и communications/composer, guards/access, reliability-and-release.md.

## Пользовательский путь первого этапа

- Название квартиры в списке квартир или таймлайне → её месячный календарь.
- Первое касание → заезд; второе → выезд. Более ранний/равный второй день становится новым заездом. Третье касание начинает новый диапазон. Смена месяца не стирает выбор.
- Диапазон, время, ночи, сегодняшний день, легенда и доступные подписи видны сразу. Открытие существующей брони — отдельная подписанная строка, не выбор дня.
- «Продолжить» → существующий мастер с той же квартирой и датами. Две даты не создают бронь.
- Свободная предвыбранная квартира пропускает повторный список. Недоступная не заменяется: можно изменить даты или явно выбрать альтернативу.
- «Новая бронь» без квартиры → тот же календарь → серверно проверенные свободные квартиры → гость/подтверждение.
- Касание свободной ячейки таймлайна задаёт только заезд, не подставляет предполагаемый выезд до следующей брони.
- Цена приходит с сервера с дневными ставками. Цена за ночь в списке обозначена как средняя, не постоянный тариф.
- Перед записью сохраняются существующие tenant/receipt/transaction/locks/audit гарантии. Пересечения повторно проверяются; изменение тарифной суммы/валюты отвергает запись до её создания.
- Ошибка/конфликт не закрывает мастер: имя, телефон, заметка, депозит и явно введённая цена остаются в состоянии компонента. Проверка обновляется; другая квартира выбирается явно.

Черновик переживает шаги и ошибки **в открытом мастере**. Полная перезагрузка, уход на другой route и восстановление после закрытия браузера не покрыты: новый постоянный PII-cache не добавлялся. Эта часть требования остаётся незакрытой.

## Реализация и границы

- BookingDateCalendar — один месячный UI для двух входов; месяц и range независимо загружаются только для выбранной квартиры. Проверка полного диапазона ловит скрытые межмесячные конфликты.
- GET /api/reservations/booking-options: ограниченный диапазон до 366 ночей; CALENDAR или RESERVATIONS для дат, только RESERVATIONS для котировок. Scope сравнивается с действующей membership, не является авторизацией.
- Результат дат содержит только ID/даты/время/roomId активных броней, без имён, телефонов, документов и сумм. У CALENDAR-only нет котировок и переходов к приватной карточке брони.
- HTTP private/no-store, браузер fetch no-store, устаревшие запросы прерываются и не используются между scopes. Существующий SW и offline dispatcher не менялись.
- nightlyTotal используется в существующем computeStayTotal и в котировке. Денежные суммы складываются в minor units. Проверка quote перед записью не применяется к явно выбранной ручной цене.
- Схема, production-миграции, Channex transaction/revision handling, build/release scripts, зависимости и дизайн-система не изменены.
- Котировки — снимок, не удержание инвентаря. Последнее решение принимает существующая серверная транзакция. Это не банковская интеграция.

### Безопасный DB-прогон для полного checkout

На новой локальной PostgreSQL с именем *_test сначала обычным тестовым процессом применить полную историю миграций. Скрипт сам не мигрирует, не загружает .env и не выполняет reset:

```sh
CALENDAR_TEST_DISPOSABLE=1 \
CALENDAR_TEST_DATABASE_URL='postgresql://test:test@127.0.0.1:5432/shanyraq_calendar_test' \
node --require ./scripts/test-server-preload.cjs --import tsx scripts/test-booking-calendar.ts
```

Создаёт уникальные синтетические fixtures в одной транзакции и гарантированно откатывает их. Проверяет computeStayTotal → сохранённую сумму/аудит, смежные брони, граничное время, чужой hotelId, устаревшую quote. Не доказывает конкуренцию разных backend-соединений и HTTP-сессию. Для unit:

```sh
npx tsx --test src/lib/reservations/date-range.test.ts
```

## Ворота и следующие этапы

1. **Завершить календарь:** полный checkout, npm ci, общий lint/TypeScript/build с неизменённым read-only schema gate; PostgreSQL script + существующие reliability/concurrency tests; HTTP auth/tenant cases; полный shell 360/390/430 и desktop; реальные keyboard/safe area; политика защищённого восстановления черновика после ухода/перезагрузки; staging smoke. Критерий — все ворота пройдены, а не только наличие UI.
2. **Единая карточка брони:** реальные независимые состояния проживания/документа/денег, один следующий CTA, существующий аудит/events и документы/composer. Новые payment/refund кнопки только после атомарного/идемпотентного сервиса FinancialOperation.
3. **Депозит/деньги:** единый типизированный ledger без двойной записи, частичные суммы и удержания, concurrency/idempotency, author/source/currency, legacy provenance без выдуманных операций. Критерий — баланс сверяется с операциями и не включается в выручку.
4. **Страница гостя:** reuse capability security, expiry/revoke/rate limit/no-store, разграничение guest/signer/payer. Нет провайдера — только явный ручной сценарий, не SaaS billing.
5. **Сценарные сообщения:** существующий composer/share, никакой автоматической отправки; надёжный scope-safe draft и ru/kk. Share не доставка.
6. **Витрина:** opt-in публикация, немедленное закрытие скрытых квартир, отдельные публичные материалы; отрицательные тесты на секреты/PII.
7. **Условия/версии документов:** override конкретной брони, неизменный принятый snapshot, новая версия/новое подтверждение; SMS только с реальным подключением, не ЭЦП; OCR только с проверкой человеком и согласованной PII-политикой.
8. **Ущерб/команда:** отдельные repair/claim/compensation сущности, пакет брони, серверно ограниченный экран уборщика без гостей/финансов. Без обещания юридической достаточности.
9. **Почасовая аренда — последняя:** сначала интервальная модель и буфер/длительность/ценообразование/каналы, не декоративный toggle и не изменение существующих ночей.

Для календаря внешние провайдеры не нужны. Для настоящих гостевых платежей/SMS позже нужны согласованные провайдеры, callback verification/credentials, staging и policies — они этим этапом не подключаются.

Merge main, production migration и deployment требуют отдельного подтверждения владельца. Этот этап их не выполняет.

## Уточнение сценария: касания внутри меню «Календарь»

После обратной связи владельца входы таймлайна изменены: они открывают **отдельный экран выбора дат внутри раздела Календарь**, а не сразу мастер брони.

- Название квартиры → `/dashboard/calendar/select?roomId=…` → месячный календарь этой квартиры.
- Свободная ячейка квартиры/дня → тот же экран с заездом из нажатой даты. Следующее касание выбирает выезд; брони ещё нет.
- Дата в заголовке → месячный выбор периода без квартиры. Доступность конкретной квартиры не утверждается до серверной проверки вариантов.
- «Продолжить» передаёт готовый диапазон и выбранную квартиру. Для фиксированной квартиры следующий экран — гость/подтверждение; для общего периода — явный выбор свободной квартиры. Шаг дат не повторяется.
- «Изменить даты» в мастере остаётся доступным. `datesSelected` — только навигационное указание, не обход tenant, quote, permissions или финальной проверки записи.
- «Назад» на экране, открытом из меню календаря, возвращает в календарь. Экран из списка квартир сохраняет возвращение к квартирам.
- Имя/ID квартиры не подменяется при чужом/невалидном roomId: сервер возвращает not-found. Экран выбора remount-ится при изменении scope, квартиры или входной даты.
- Кнопки в заголовке и свободные ячейки desktop/расширенного таймлайна используют тот же маршрут. Нажатие существующего блока брони по-прежнему открывает её детали.

Добавлены 4 unit-теста переходов (итого 12/12). Повторно прошли lint затронутых файлов и та же ограниченная строгая проверка TypeScript/Prisma contracts. В локальном Chromium реальные MobileCalendar → ApartmentCalendar → MobileNewReservation проверены с навигационным/HTTP-стендом: название квартиры, свободная ячейка, дата в заголовке, диапазон через месяц, отсутствие auto-submit и повторного ввода дат, явный выбор квартиры. Ширины 360/390/430/1280 px, ru/kk. На 1280 проверена ширина экранов выбора и мастера, **не полный desktop CalendarBoard**. Прежние конфликтные проверки мастера повторены.

Полный Next.js build, HTTP-сессия с реальной PostgreSQL, desktop/PWA shell и staging по-прежнему не подтверждены. В этом дополнении нет миграций, изменений бизнес-записи, финансов, провайдеров, merge или production deploy.
