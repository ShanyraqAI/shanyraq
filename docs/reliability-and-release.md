### Повторы и хранение результатов

Ключ связан с `userId + hotelId + key`, именем действия и SHA-256 канонического запроса. Один ключ с другими аргументами отвергается. Повтор сначала проходит актуальную авторизацию, затем получает первоначальный результат. Неуспешный бизнес-результат откатывает транзакцию и не создаёт receipt.

Receipt не хранит исходный текст заметки/профиль гостя: только хеш запроса и результат действия (ID/сообщение). Автоматического TTL нет: удаление receipt при существующей офлайн-очереди снова разрешило бы дубль. Политику хранения нужно согласовать вместе с максимальным возрастом очереди и запретом старых повторов. Не очищать receipt независимо от этого протокола.

Очередь v1 не переименовывается в v2 и не отправляется автоматически: её первичная попытка могла уже выполниться на старом сервере. Пользователь должен проверить результат и удалить старую запись; при необходимости выполнить новое действие вручную. Подмена ключа при повторе недопустима.

### Channex: старые данные и неоднозначный порядок

`lastRevisionAt` старого кода — время локальной обработки, не время провайдера. Новое nullable-поле `lastProviderRevisionAt` намеренно не заполняется этим значением миграцией.

Перед включением обработки для уже существующих броней:

1. Приостановить polling конкретного объекта и дождаться завершения старых воркеров.
2. В Channex staging сверить актуальную booking/revision и локальные комнаты, даты, статус, сумму и комиссию. Проверить, что provider timestamp действительно задаёт монотонный порядок; не брать локальное время или UUID.
3. Если состояния совпадают, отдельно одобрить запись подтверждённого provider watermark для конкретной `propertyRefId + channexBookingId`, с аудитом и резервной копией. Массовое заполнение `NOW()` запрещено.
4. Если состояния расходятся или две revisions имеют одинаковую отметку, сначала выполнить контролируемую сверку/восстановление. Не обходить блокировку слепым backfill.
5. Повторить сохранённые FAILED revisions и проверить результат до восстановления polling.

Новые брони получают watermark в одной транзакции с первой применённой revision. Сбой ACK не откатывает локальную бронь: повтор подтверждает уже обработанное событие, не создавая его заново.

## Воспроизводимые проверки

Без базы:

```sh
npm ci
npm run test:reliability
npx tsc -p tsconfig.reliability.json --pretty false
npx prisma validate
```

`prisma validate` требует `DATABASE_URL`, но не подключается к БД. Для проверки схемы использовать фиктивный локальный URL, а не production-секреты.

С базой — **только отдельная одноразовая PostgreSQL БД с именем, оканчивающимся `_test`**. Сначала на ней применить всю историю миграций обычным тестовым процессом. Затем:

```sh
RELIABILITY_TEST_DISPOSABLE=1 \
RELIABILITY_TEST_DATABASE_URL='postgresql://test:test@127.0.0.1:5432/shanyraq_reliability_test' \
npm run test:reliability:db
```

Скрипт не загружает `.env`, подменяет `DATABASE_URL` только явно указанным тестовым URL, создаёт уникальные синтетические fixtures и удаляет только их. Он не выполняет `reset` и не мигрирует рабочую БД. `test-server-preload.cjs` снимает только bundler-маркер `server-only` в отдельном тестовом процессе: авторизация, Prisma и бизнес-методы не подменяются. Это не тест Next.js action transport/реальной браузерной сессии.

Проверяемые сценарии:

- Потерянный ответ после записи: повтор возвращает тот же ID и одну запись аудита.
- Ошибка аудита: нет новой брони, изменений availability и receipt.
- Повтор добавления заметки: одна заметка, не две.
- Разные люди с одинаковым именем и общим email; явный чужой guest ID отвергается; две Excel-строки с одинаковым именем создают отдельные профили.
- Вторая комната revision с ошибкой: откат первой комнаты, гостя, связей и ARI job.
- Повтор той же revision, новая revision с прежним systemId, обратный порядок и равное provider-время.
- 160 профилей гостей: по 50 строк; у выбранного гостя 45 броней/45 заметок — страницы 20/20/5; поиск и tenant-фильтры.
- Очередь до первой отправки, потеря ответа, смена scope до записи очереди, повреждённый legacy storage.
- SW: онлайн-HTML не кешируется; без сети приватный URL не получает старый HTML; activation очищает legacy cache; старое warm-сообщение не возвращает кеширование.
- Release: обычный build не содержит миграций, случайный запуск migrate без approval отвергается, старый deploy-helper не обходит новую границу.

### Фактически выполненная проверка этой ветки

- Unit/регрессионные тесты: 32/32 успешно. Строгая проверка изменённого графа `tsconfig.reliability.json` и ESLint изменённых JS/TS-файлов с `--max-warnings 0` прошли. Prisma validate и schema diff проверены; миграция только добавляет receipt-таблицу, provider watermark и два индекса.
- Интеграционные сценарии выполнялись реальными Prisma/сервисами на временном PGlite PostgreSQL-движке через локальный wire proxy. Использовалась схема baseline из Prisma + новая аддитивная миграция, **не полная историческая цепочка**. Это подтверждает проверенные rollback/replay/query-сценарии, но не доказывает конкурентные advisory locks разных PostgreSQL backend-соединений и совместимость всех старых SQL-триггеров.
- В локальном Chromium на синтетическом HTTP-стенде проверены фактическая активация текущего SW, удаление старого page-cache, две вкладки с разными scopes и общий offline-экран вместо приватного HTML. Это не проверка iOS/Android PWA и не вход в production.
- Полный checkout/build в Vercel, production БД, реальный Channex staging ACK, полноценная пользовательская сессия и реальные мобильные устройства этим прогоном не проверялись.

## Обязательные ворота перед production

1. Review изменений; полный чистый checkout; `npm ci`, общий lint, полный TypeScript/build и существующие тесты. Точечный `tsconfig.reliability.json` не заменяет полный build.
2. Отдельная PostgreSQL БД из production-подобного backup без реальных персональных данных; прогнать всю историю миграций и сценарии выше. Отдельными соединениями одновременно повторить один ключ, разные revisions одной booking и разные multi-room bookings; проверить deadlocks/повторы после падения воркера.
3. Проверить одноимённых гостей в UI, поиск и переходы страниц, notes-tab, возврат после редактирования. Нагрузочные EXPLAIN/тайминги на ожидаемом объёме.
4. На настоящих PWA проверить смену пользователя/объекта, выход в другой вкладке, возврат из background/BFCache, истечение сессии без сети и обновление старого SW. Старые открытые клиенты закрыть перед rollout; legacy-очередь проверить вручную.
5. Подтвердить Channex timestamp/порядок на staging и выполнить сверку legacy watermarks. Внешние провайдеры из старого `provider-registry` — mock-адаптеры, не подтверждённые production-интеграции. Этим PR они не включаются.
6. Согласовать резервную копию и восстановление; проверить расширяющую миграцию со старой версией приложения. Добавление обычных индексов может блокировать запись: выбрать окно по объёму таблицы или отдельно согласовать concurrent-index план. Не переписывать применённые SQL-миграции.
7. Собрать **неизменяемый Ready deployment нужного SHA** с будущей схемой на staging, выполнить smoke-тест. Одобрить миграции в защищённом release-окружении. Только после этого отдельно запустить:

```sh
VERCEL_ENV=production RELEASE_MIGRATIONS_APPROVED=1 npm run db:migrate:release
```

Здесь `DATABASE_URL`/direct migration URL должен быть установлен владельцем release-окружения и указывать на проверенную целевую БД. Команду нельзя добавлять обратно в Build Command Vercel. После успешной миграции продвинуть **уже проверенный** deployment, а не запускать новую сборку. Если это невозможно в текущем процессе/тарифе, нужен отдельно согласованный maintenance rollout, а не обход через миграции внутри build.

Если build падает — production-миграции не запускать. Если promotion не удался после аддитивной миграции — оставить совместимую старую версию и остановить выпуск; не удалять данные/колонки автоматически. Перед откатом на сервер без протокола v2 остановить mutation/replay-трафик: новый клиент нельзя направлять на старый сервер, игнорирующий ключи. Предпочтительно forward-fix. Восстановление backup требует отдельного решения с учётом записей после backup, а не автоматического reset.

**Этот PR не применяет production-миграции, не сливает main и не выполняет production-деплой.**
